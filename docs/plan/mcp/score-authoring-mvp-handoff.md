# MCPによる譜面新規構築MVP：要件・設計方針・引継ぎ

更新日：2026-11-09（日本時間）

## 1. 再開時に最初に読むこと

**当面の目標は、エージェントが空のプロジェクトへまとまった譜面を記述し、整合した譜面をGUIで確認できること。既存音符の修正機能を先に充実させる方針ではない。**

将来、Codexなどが楽譜画像を読み、読み取った内容をClavierDeskへ入力する。呼び出し回数、入力・応答のトークン量、再送やエラー修正のコストを重視する。画像認識そのものをアプリやMCPサーバーに実装することは、このMVPの対象ではない。

ユーザーは本資料の設計方針で進めることに合意している。ただし、構築APIの実装にはまだ着手していない。本資料中の新しい操作名・JSON形式・エラー例は設計案であり、現在呼び出せるAPIと混同しないこと。

読む順序：

1. 本資料：目的、MVP範囲、構築APIの方向、再開手順。
2. [チェックアウトとUI入力](./checkout-and-ui.md)：実装済みの排他・一括反映・停止。
3. [MCP README](../../../code/apps/mcp/README.md)：現在のツール・ビルド・登録。
4. [既存アーキテクチャ](../score-domain-model/architecture.md)と[譜面モデル](../score-domain-model/score-domain-model.md)。

[旧引継ぎ資料](./handoff.md)は接続MVP当時の記録。本文にある「参照・編集は未実装」「未コミットファイル」「テスト件数」等を現在の事実として使わない。新規構築の方針は本資料、現在の挙動はコードとチェックアウト資料を優先する。

## 2. ユーザーと合意した要件

| 項目 | 方針 |
| --- | --- |
| 当面の成果 | 空の状態から、AI主体でまとまった譜面を作成し、GUIで確認する。 |
| 編集APIの中心 | 音符1個ずつの操作ではなく、完成させたい小節群の構造を渡す。 |
| 修正機能 | 当面のMVPではなくてもよい。運指編集の拡張を先行させない。 |
| ツール構成 | 操作ごとにMCPツールを増殖させず、共通の`apply_edit`へ型付きの構築操作を渡す方向。 |
| 効率 | 全曲の一括送信と、画像の段・ページ等に応じた分割送信の両方を可能にする。 |
| 内部ID | 新規入力で既存IDを要求しない。永続IDや参照の生成はアプリ側で行う。 |
| 整合性 | 入力形式だけでなく、時間・参照・内部構造を検証し、不整合な状態を実プロジェクトへ反映しない。 |
| 実データへの反映 | チェックアウト中は作業用データへ蓄積し、最後に一度だけ反映する。 |
| 強制停止 | 未反映データを破棄し、所有権とUIロックを解除。遅延した旧要求を拒否する。 |
| 完了・停止通知 | 先にロックを解除し、その後で通知する。OKやEscapeによる解除を条件にしない。 |
| 未確定のUI入力 | チェックアウトを拒否して下書きを維持する。自動確定・破棄しない。 |

ユーザーはMCPの実GUIとの通し確認を、後でまとめて行う予定。フロートテキストのGUI確認についてはユーザーから確認した旨の返答があった。再開時に、実GUIでのMCP編集・停止まで検証済みと扱わないこと。

## 3. 現在の実装と、これから作るもの

### 実装済み

- ローカルstdio MCP → 認証付きループバックHTTP → Tauri → WebViewの接続。
- 公開セッションの検出・疎通、Ctrl＋Mでの公開切り替え。
- `begin_checkout`による所有権と固有の`checkoutId`の発行。
- 作業用プロジェクトへの運指編集と、その状態の取得。
- `finish_checkout`で一括反映、変更時のみUndo履歴1件、所有権解除、UIロック解除、その後の通知。
- `Stop MCP editing`ボタン／Ctrl＋Shift＋Mによる作業用データの破棄・解除。
- 旧`checkoutId`の拒否。同一エージェントが再取得しても旧要求は通さない。
- UI変更入口の共通判定、キー入力抑止、`inert`とポインター遮断、未確定入力等がある場合の開始拒否。
- Scorehackを参考にした独自フロート入力。HTML inputを使わず、文字列とカーソルを共通キー経路で更新する。外観も黒背景・白文字・等幅文字・縦線カーソルに合わせている。

現在公開しているツールは7個：`ping`、`list_clavierdesk_sessions`、`probe_session`、`begin_checkout`、`get_editor_state`、`apply_edit`、`finish_checkout`。

**現在の`apply_edit`は、単一の`operation: "set_pitch_fingering"`と運指用の引数を受け取るだけ。`operations`配列・`create_score`・`append_measures`・`requestId`は未実装。**

### 未実装

- 譜面構築用の入力型・実行時検証・JSON Schema。
- 空からの構築、小節群の末尾追加、入力記述から内部譜面への変換。
- 操作配列全体の原子的適用、要求の再送重複排除。
- 構築中の小節境界をまたぐ接続予定と、その解決。
- 詳細な構造・参照整合性検証、構築エラーの位置付き診断。
- 新規構築後にGUIの最初の小節へ表示・フォーカスを合わせる処理。

自動切断検知・リース期限は未追加。手動強制停止を復旧手段とすることで合意しており、当面の必須追加ではない。

## 4. 構築APIの設計方向

### 4.1 最小の構築操作

操作名は仮称。次の2種類から始める。

| 仮称 | 内容 |
| --- | --- |
| `create_score` | 空のプロジェクトに初期設定と小節群を構築する。 |
| `append_measures` | 作業中の譜面の末尾へ小節群を追加する。 |

流れは`begin_checkout → create_score → append_measures（必要回数）→ finish_checkout → GUI確認`。

既存曲の置換・途中挿入・削除・範囲修正は構築MVPの必須条件にしない。「空」の厳密な判定は実装前に定める。既存内容を黙って上書きする動作にはしない。

### 4.2 入力形式の案

以下は実装済みのリクエストではない。実装前に、型・バリデーション・ツール説明を同じ仕様へ揃えること。

```json
{
  "sessionId": "...",
  "checkoutId": "...",
  "requestId": "page1-system1",
  "operations": [
    {
      "type": "create_score",
      "settings": {
        "meter": [4, 4],
        "keyFifths": 0,
        "tempo": 100
      },
      "measures": [
        {
          "upper": [
            [
              { "value": "4", "pitches": ["C5", "E5"] },
              { "value": "4", "pitches": ["D5"] },
              { "value": "2", "rest": true }
            ]
          ],
          "lower": [
            [
              { "value": "1", "pitches": ["C3", "G3"] }
            ]
          ]
        }
      ]
    }
  ]
}
```

- 小節ごとに上下段を記述し、その内側に声部ごとのイベント列を置く。
- 声部内は順番と音価で開始位置を導出する。通常入力で毎音符の開始位置を書かせない。
- 音価の案は`"1"`＝全音符、`"2"`＝二分音符、`"4"`＝四分音符、`"4."`＝付点四分音符等。正確な文法は実装前に固定する。
- 音高の案は絶対音名。`C4`を中央ドとし、調号によって文字列の音高が暗黙に変わらない規則にする。
- 和音は1イベントに複数音高を指定する。永続IDと位置は生成する。
- 拍子・調号・テンポ等を上位で指定し、繰り返しを減らす。
- 小節や音符を匿名の数値配列へ過度に圧縮せず、型で意味を判別できる構造にする。単発の文字列DSLを先に作ることは合意していない。

### 4.3 補完するものと、拒否するもの

ID生成、位置計算、音高の内部形式への変換、共通設定の継承、音高の並べ替えと付随情報の保持はアプリ側で行う。

**指定された声部の音価合計が足りない場合は、既定ではエラーにする。** 読み落とした音符を休符で埋めて成功扱いにしない。休符は明示し、段全体を省略した場合だけ全小節休符にする方向。空配列、声部の省略、声部数が小節間で変わる場合の詳細は未決定。

小節を超える音価、不正な音高、無効な連符、成立しない接続、現モデルで表現できない指定は、場所を示して拒否する。未対応指定を黙って無視しない。

### 4.4 連符・タイ・分割送信

- 連符は比率・基準音価・中のイベント列をひとまとまりで記述する。通常音符の浮動小数の開始時刻に分解して渡さない。
- タイは同じ段・声部の次の音符への継続を記述し、内部IDの接続はアプリ側で生成する方向。正確なフィールド名は未決定。
- 小節間で声部の対応を維持する。現モデルは段ごとに最大3声部。
- 分割送信の末尾に未完のタイがある場合は、構築セッションの「接続予定」として保持し、次の追加で解決する案。
- 接続予定は不正な永続参照として保存しない。未解決の接続を残したままの`finish_checkout`は拒否し、作業用データを維持して追加入力または強制停止を可能にする。

現モデルでのタイは音符／和音全体を接続する。和音の一部の音だけのタイを、対応済みと扱わない。

### 4.5 適用の原子性

二段階の境界を維持する。

1. **1回の`apply_edit`**：配列を順に候補データへ適用し、全件成功したときだけ作業用データを更新する。失敗した要求全体を取り消し、それ以前の成功要求は維持する。
2. **`finish_checkout`**：全体検証に成功した場合だけ、作業用データを実プロジェクトへ一度だけ反映する。

候補データには小節数・声部の音価等の構造整合性を保つ。将来送られる小節との接続予定だけは、別の構築状態として明示的に扱う。任意の不整合を後続操作で修復できる汎用パッチ言語へ広げない。

### 4.6 再送・応答・読み取り

- `requestId`等で小節の二重追加を防ぐ。同じID・同じ内容は以前の結果を返し、同じID・異なる内容は拒否する方向。記憶の範囲はチェックアウト内を基本とし、正確な仕様を実装前に固定する。
- 成功応答は小節範囲・音符数・未解決接続等の要約を基本とする。毎回全プロジェクトや全音符IDを返さない。
- 診断は操作番号・入力内の小節位置・段・声部・イベント位置を返し、問題箇所へ戻れるようにする。例：「入力2小節目・上段・声部1が四分音符分不足」。
- 必要な場合だけ範囲指定で読み取る方向。条件検索・投影・詳細な参照ツールは将来拡張であり、構築MVPの先行条件にはしない。

## 5. 整合性と、現モデルで注意する点

現在の[保存用バリデーター](../../../code/apps/editor/src/domain/score/score-project-validator.ts)は、構造・フィールド・声部の音価合計等を確認するが、IDの一意性や全参照の成立を包括的に保証するものではない。これだけで構築結果の整合性保証が完成すると扱わない。

新規構築では、入力形式 → 小節・声部・音価 → 内部プロジェクト生成 → ID・参照・時間関係という段階で検証し、最終反映前にも全体を確認する。時間は既存の有理数演算を利用し、連符を浮動小数の近似で検証しない。

| 既存モデル・実装 | 設計上の注意 |
| --- | --- |
| 音符・休符の音価は全音符～32分音符、付点を保持 | 入力文法と実際に保存・描画できる範囲を一致させる。 |
| `PianoTuplet`はグループを保持 | 保存用検証とdomainで許容条件に差があるため、対応する連符の範囲を揃える。 |
| 音高はMIDI＋綴り方向ヒント | 入力音名の異名同音を厳密に保存できるとは限らない。対応綴りを確認し、未対応は明示する。 |
| UIの和音幅制限・他声部との同音衝突判定 | 音楽全般の不整合とは別物。UI操作制限を無条件に構築APIへコピーしない。保存・描画・後続編集を確認して方針を決める。 |
| タイ等のreconcileは不成立参照を除去することがある | 不正な入力を黙って消して成功扱いにしない。構築入力では診断して拒否する。 |
| `RestSpelling`は通常の32分単位グリッドを前提 | 連符内外の時間を混同しない。 |

「整合した譜面」と「原画像と一致した譜面」は別の検証。アプリはデータの成立を検証し、画像の読み間違いはエージェント／ユーザーが表示結果と比較して確認する。

## 6. GUIでの完成条件

`project`を代入するだけで終了しない。新規構築後は有効な小節へアウトライン・タイムラインのカーソルを合わせ、GUIの最初の小節と譜面プレビューを確認できるようにする。空だった旧プロジェクトのフォーカスを残さない。

チェックアウト中の作業用譜面のライブプレビューはMVPの必須条件ではない。まずは`finish_checkout`後に確認できればよい。途中確認が必要なら、整合した単位で終了して確認する運用、または将来のプレビュー機能を別途検討する。

初期設定は固定の拍子・調号・テンポを基本とし、上下段・複数声部、通常音符・和音・休符・付点、基本的な連符、現モデルで表現できるタイを扱う方向。

途中の拍子・調号・テンポ変更、弱起等の特殊な小節、装飾音・スラー・ペダル・トリル等の詳細表現、部分和音タイ、既存曲の修正は、MVPに自動的に追加しない。入力型は将来の拡張を妨げないようにする。

## 8. 実装前に固定する詳細

大方針を再議論する必要はないが、次の細部は仕様と実装を揃える必要がある。新たなユーザー判断が不要なものは、合意済みの目的に沿って具体化する。

1. 構築操作名、設定の必須項目・既定値、空プロジェクトの判定。
2. 音価文字列、絶対音名・臨時記号の文法と、表現可能な綴りの範囲。
3. 声部の識別・省略規則、未指定段と空配列の違い。
4. 連符、タイ継続、分割境界の接続予定の正確な型。
5. 全体検証の項目、許可する音域・和音・声部間の重複音等の制約。
6. `requestId`の重複判定、失敗要求の再送、タイムアウト後の結果確認。
7. 1要求の上限、診断・応答の上限、エラーの構造。
8. 既存の運指用`apply_edit`からのスキーマ移行。互換維持・廃止方法は未決定だが、運指機能の充実を優先しない。

現ブリッジは要求本文64 KiB、MCP側HTTP応答全体256 KiB、WebView応答待ち5秒。大きな譜面ではこの制限を実測し、分割送信と処理上限を設計する。無制限の全曲送信が可能と説明しない。MCP世代管理の追加は今回の合意範囲ではない。

## 9. MVPの受け入れ確認

1. 起動直後の空プロジェクトから、既存音符IDなしで両手8小節程度を構築できる。
2. 和音・休符・付点・複数声部・基本的な連符・小節をまたぐタイを含む例で、GUI表示まで確認する。
3. 一括送信と複数回の追加で、生成IDを除いた譜面内容が一致する。
4. 音価不足・超過・不正参照等は位置付きで拒否し、失敗した要求が作業用データを部分更新しない。
5. 同じ要求の再送で小節が二重追加されない。異なる内容で同じIDを使う場合は拒否する。
6. 分割境界のタイを解決でき、未解決なら最終反映を拒否する。
7. `finish_checkout`で一度だけ反映し、Undoで構築前へ戻せる。最初の小節へフォーカスが移り、プレビューを確認できる。
8. 反映前の強制停止は全変更を破棄し、再チェックアウト後にも旧要求を拒否する。
9. 未対応の記譜を勝手に近似・省略して成功扱いにしない。

構造検証とGUI描画の確認を分ける。MCP応答成功だけで、譜面が正しく表示されたと判断しない。

## 10. 作業ツリー・検証状況・別環境への移行
