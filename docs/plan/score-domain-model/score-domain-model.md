# ソロピアノ譜エディタ：ドメインモデルと検証方針

最終整理日：2026-10-26

この資料は、Scorehackを基準にしたソロピアノ譜エディタの目的、合意済みの設計判断、未決事項、段階的な開発方針を記録する。最終仕様を一度に固定するものではない。検証アプリで操作とモデルを確かめ、判断が必要になった段階でこの資料を更新する。

## 1. 目的

作曲・編曲者が白紙からソロピアノ譜を入力・管理できるアプリを作る。主な価値は次の二つ。

1. ピアノロールを基準に、キーボードだけで音を速く入力でき、内部データは小節・声部・音価・タイなど楽譜として整合する。
2. ノートに割り当てた指番号を使い、将来3Dの手・指の動きで演奏をプレビューできる。

重みは譜面ドメインと入力体験がおよそ8割、3Dプレビューがおよそ2割。まず譜面モデルと編集の土台を検証する。初期版は完成品ではなく、理解が進んだ時点で作り直すことも前提とする。

主な用途は新規作成。MusicXMLの読み込みは将来対応したいが、アプリ内モデルで表現できる範囲をピアノ譜に限定するため、未対応要素や取り込み時の情報欠落を検出・説明する設計が必要になる。

## 2. Scorehackを基準にする範囲

Scorehackをゼロから置き換えるのではなく、既存のキーボード操作・ピアノロール・アウトラインの考え方を出発点にする。

### 引き継ぐ考え方

- OutlineとTimelineを切り替えるモード構成。
- マウスを使わず、キーボードだけで入力・移動・選択を完結させる。
- ノートの実音価と、移動・入力に使う操作音価を別に管理する。
- 操作音価に合わせてノート音価を正規化する。
- カーソル、選択位置、アウトラインのフォーカスとスクロールを同期・自動追従させる。
- 拍子、テンポ、調号などの音楽上の基礎情報を扱う。
- 88鍵の音域を持つピアノロールを基本の入力画面とする。

Scorehackの既存操作や実装を必要に応じて参照する。特にキーリピート中のスクロール追従、音価の操作単位と実音価の分離、フォーカス表示を参照する。

### 引き継がない考え方

- ディグリーやコード進行を中心にした作曲モデル。
- 「伴奏」と「メロディ」を別トラック・別責務として分けるモデル。
- 歌詞入力。

コードを直接編集できることを中心にせず、音符と声部からピアノ譜を組み立てる。

## 3. データの基本構造

概念上の関係は次の通り。ペダルは初期段階では実装せず、関係も後で決める。

```text
Project
├─ Initial values
├─ Outline: ordered, parallel blocks
│  ├─ Section marker
│  └─ Measure block
│     ├─ Upper staff
│     │  └─ Voices[]
│     │     └─ Notes[]
│     │        └─ Pitches[] (each pitch may have fingering)
│     ├─ Lower staff
│     │  └─ Voices[]
│     │     └─ Notes[]
│     └─ Pedal (future; structure undecided)
└─ Position-based musical events (e.g. tempo, future clef changes)
```

Outlineの実データでは、初期値ブロック、セクションブロック、小節ブロックを一つの順序付き配列に並列で置く。小節配列をセクションの子としてネストしない。セクションはアウトライン上の境界・移動単位であり、後続する小節が直前のセクションに属することを表す。

小節は内部に上段・下段を持ち、それぞれ複数声部を持つ。声部はデータ構造そのものとして扱い、単なる譜面の見た目設定とはしない。ノートは一つの声部に属する。小節を削除すれば、その小節内に属する譜表・声部・ノートも削除される。

最初の入力対象は上段のvoice 0だけでよい。ただしデータは最初から上下段と複数声部を表現できるようにする。UIでは上下段を同じピアノロールで扱い、初期段階の操作対象を限定する。

### ノートとピッチ

- 現段階で「ノート」と呼ぶ単位は、開始位置と長さを持つ時間上の一つのまとまり。
- 一つのノートは複数のピッチを持てる。したがって和音は同時開始・同一音価のピッチ配列で表現する。
- ノート内の全ピッチは開始位置・長さ・タイ構造を共有する。和音の一部の音だけ長さやタイを変える構造にはしない。独立した長さが必要な音は別ノートとして別声部に置く。
- 指番号はピッチごとに保持する。
- 「ノート」という名称が時間まとまりを指すのに適切かは、実装を進めてから再検討する。

### 位置と音価

実音の位置・長さはミリ秒でなく、楽譜上で正確に扱える拍・音価ベースの値で表す。現在の検証アプリでは開始位置を小節内の16分音符ステップ、音価を分数で表している。これは入力検証の現行表現であり、連符などを含む長期モデルの最終表現は別途検討する。

操作音価はカーソルの移動・新規入力に使い、ノート音価とは独立させる。現行UIの`1`・`2`・`3`キーは16分・8分・4分を選ぶ。実音価は入力・伸縮・結合時に楽譜上で扱える音符へ正規化する。

## 4. 拍子・小節・アウトライン

- 初期値ブロックはそのまま設ける。初期値の調は長調・短調でなく調号（五度圏の`fifths`）として扱う。
- 拍子は分子・分母を持つ。複合拍子では、操作・時間表示上の1拍を付点4分音符として扱う。
- 拍子と小節ブロックの実際の長さは別の値として持つ。
- 変拍子、弱起、終止の短い小節などのため、拍子の標準長と異なる長さの小節を許容する。例：4/4の曲の開始に1/4小節を置く。
- セクションは譜面上の必須記号ではなく、アウトライン上のまとまりとカーソル移動単位として保持する。
- 調号・拍子の変更は小節境界で扱う方針。テンポは調号・拍子のような小節単位ブロックと同じ扱いにせず、時間位置に置かれ、そこから有効になるイベントとして考える。
- テンポや将来の音部記号は「ノートに対して指定する」操作を想定するが、特定のノートに所有させるわけではない。内部保存形式やMusicXMLへの対応付けは実装時に決める。

小節長を変更したときに、別の小節に所属するノートの位置・長さが連鎖して変わることはない。小節を短くして範囲外になるノートをどう処理するかの詳細は後の編集機能設計に送る。現時点で共有されている想定は、警告を出し、範囲外ノートを削除し、次小節のノートとつながっていたタイを解除すること。

## 5. 音価の正規化とタイ

入力操作はピアノロール基準とし、音符・休符を手で数えて小節を埋める負担をなくす。一方、保存データは最終的に譜面として整合する構造にする。

### 操作音価と実音価の例

操作単位が16分音符の場合、長さを1ステップずつ伸ばすと、例えば次のように正規化する。

| ステップ数 | 正規化された音価 |
|---:|---|
| 1 | 16分音符 |
| 2 | 8分音符 |
| 3 | 付点8分音符 |
| 4 | 4分音符 |
| 5 | 4分音符＋16分音符をタイで接続 |
| 6 | 付点4分音符 |
| 7 | 4分音符＋付点8分音符をタイで接続 |
| 8 | 2分音符 |
| 16 | 全音符 |

通常の操作では、入力グリッドに対して不自然な位置に大きな音価を直接置くのではなく、正規化された音符に分解する。例えば16分グリッド上の5ステップは、4分音符と16分音符のタイ接続で表す。

### タイ列の編集

- タイは最終譜面の見た目だけで後付け生成する情報ではなく、入力モデル上でも保持する。
- ノートを伸ばすと、正規化境界で一つのノートが確定し、後続のノートが作られてフォーカスが移る。
- 短くすると、必要に応じて直前ノートへフォーカスを戻し、後続ノートを削除する。
- 移動・長さ変更では、つながっているノート列全体を連結・分割・再正規化する。
- 例として4分音符＋16分音符のタイ列を1ステップ伸ばすと、付点4分音符へ再結合する。
- 小節をまたぐ長さも小節ごとのノートに分け、タイで接続する。4/4の3拍目から8ステップ分を伸ばす例は、当該小節の4分音符と次小節の4分音符をタイで接続する。
- タイの`from`／`to`など具体的な永続表現は後で決める。和音ノートでは全ピッチが同じタイ構造を共有する。

### 休符

通常のピアノロール入力に休符を直接置く操作は設けない。空白区間から声部ごとの休符を求める考え方を基本とする。一方、保存データだけで譜面を表現する方針も検討中であり、休符を永続データとして保持するか、導出またはキャッシュするかは未決事項。MVPでは休符の手入力・描画・MusicXML変換を実装しない。

### 連符

現時点で通常の音価正規化ルールは合意しているが、三連符などの連符グルーピング・比率・入力操作は未決事項。16分刻みの整数だけで将来の音価を表現できると決めつけず、連符を具体的に扱う段階で位置・長さ・グループ構造を検討する。

## 6. 調号・実音・譜面上の音名

- 調号変更後も、既存ノートの実際に鳴る音は維持する。
- 調号を変えた結果、譜面上の音名・臨時記号は調号に沿うように再表記したい。例えばF majorからC majorへ変えたとき、元からB♭として鳴っていた音は実音を保ったままフラット表記になる想定。
- 調号に照らして不自然な異名同音表記（例：F majorの文脈でA♯と保持する）を許すべきではない。
- したがって、実音高（現在の実装ではMIDI pitch）と譜面上の音名・臨時記号をどう導出・保持するかを分けて設計する必要がある。
- 「音名を完全に自動算出するか」「ユーザー指定の綴りを保持するか」「調号変更時に明示的な再表記を行うか」、臨時記号の小節内適用規則や異名同音の例外は未決事項。ディグリーを入力モデルに持ち込まない。

## 7. MusicXMLの位置づけ

MusicXML互換は単なる他アプリとの連携要件ではなく、譜面データとして整合したドメインモデルを設計するための基準である。ミリ秒だけのノート、声部のない音の羅列など、楽譜として不十分な独自モデルにしない。

- 主目的は内部データの音楽的・記譜的な整合性を保つこと。
- MusicXML出力後にMuseScoreで開いたとき、ノート・小節・声部・タイ・調号などのレイアウトが壊滅的にならないことを妥当性の確認に使う。
- MuseScoreとの完全な往復互換、強弱・アーティキュレーション・スラー・ペダル・ページレイアウト等の全要素保持は当面の要件ではない。
- MusicXML読み込みは将来対応。アプリ内で表現できない要素は、黙って不正確に読み込むのではなく、取り込み前後に非対応・欠落を把握できる仕組みが必要。
- MusicXMLの詳細な要素対応表、インポート時の制約、譜面の見た目の調整方法は、譜面出力に進む段階で仕様化する。

## 8. ペダル・運指・3Dプレビュー

### ペダル

ペダルは初期段階では扱わない。MusicXML上のペダル表現を調べた上で、独立したペダルレイヤーにするか、下段のノートと関連付けるかを後で決定する。

### 運指

ピアノ音高ごとに指番号1〜5を保持できる構造を目標とする。運指の自動割当、両手間の整合、交差・持ち替え等のルールは別途設計する。まずは譜面側の指定を3Dプレビューへ渡せることを優先する。

### 3Dプレビュー

プレビューは譜面ドメインが主、3D表示が従の位置づけ。ノートの開始・長さ・ピッチ・手・指番号を3D側へ渡せる境界を設計する。演奏動作の補間や手の運動学は3D Motion Lab側で別途検証し、このエディタの譜面モデルに演奏秒数だけを持たせる設計にはしない。

## 9. UIと入力の初期方針

- レイアウトはScorehackを基準にし、左をOutline、残りをTimelineのメイン領域にする。
- Timelineは時間軸ヘッダ、ピッチ一覧、ピアノロールで構成する。ヘッダとピッチ一覧はピアノロールから独立してスクロールする。
- 上段・下段は同じピアノロールを使う。上下段や非アクティブ声部の見せ方・切り替え方は実装時に詰める。
- 初期検証では上段voice 0のみを編集する。
- アプリ内の正式な表示文言は英語で統一する。検証用の開発メモは日本語可。
- マウスを使わず操作を完結させる。スクロールバーは見せず、カーソル移動に合わせて必要な領域を自動スクロールする。
- Scorehackと同様、画面幅に応じたレスポンシブ再配置は行わず、最低フレームサイズを基準にする。Tauri導入時に最小サイズを設定する。
- 初期版は新規プロジェクトの検証画面から始め、エントリー画面やファイル選択は設けない。

## 10. 現在の検証アプリ

実装先は`apps/editor`。Svelte 5 + TypeScript + Viteで進め、Tauriへの移行は本格開発時に検討する。

現時点のプロトタイプには、初期値・セクション・小節を持つOutline、上下段と複数声部を含む最小プロジェクトモデル、上段voice 0の単音入力、Timelineのフォーカス、操作音価、88鍵ピッチ表示がある。キー入力でノートを置き、既存ノートにフォーカスし、フォーカス中に上下でピッチを変更できる。音価・調性によるノート表示と列フォーカス、キーボード操作に応じた自動スクロールも検証対象。

この実装は検証用であり、最終ドメインAPI、保存形式、譜面レンダラーを確定したものではない。和音の入力、複数声部・上下段の切り替え、ノートの移動・長さ編集とタイ列の再正規化、休符、MusicXML入出力、ペダル、運指入力、3D連携は段階的に扱う。

## 11. 未決事項・再検討する境界

以下は未確定である。後の仕様決定時に必要な問いを追加し、確定事項と混ぜない。

1. ノート音価を表す最終的な正確値、連符の比率とグループ化。
2. 休符を永続データにするか、声部の空白から導出するか、またはキャッシュするか。
3. 調号変更時の異名同音表記、音名の自動推定・明示指定、臨時記号の規則。
4. タイの識別子・from/to表現、和音とタイのMusicXML対応。
5. 拍子変更時に既存小節の実長をどう変えるか。別小節へノートを移動・シフトしない原則は維持し、具体的な再区切り操作はその機能の設計時に決める。
6. セクション境界と小節の所属を、フラットな配列からどう導出・検証するか。
7. テンポ・音部記号等の位置イベントの保存形式と、MusicXMLへの対応。
8. ペダルのドメイン構造と、下段との関係。
9. MusicXMLで最初に出力・入力する要素、およびMuseScoreで妥当な譜面表示を確認する方法。
10. 和音入力時のピッチ単位フォーカス、上下段・複数声部の切り替えUI。
11. 指番号の手入力・自動提案と、3Dプレビューに必要な演奏情報の境界。

## 12. 段階的な進め方

一度に全仕様・全機能を作らない。各段階で操作感とドメインの妥当性を確認し、次の段階へ進む。

1. Outline・Timelineのレイアウトとキーボードフォーカスを整える。
2. 初期値、セクション、小節ブロックを表示・追加し、カーソル同期と自動スクロールを確認する。
3. ピアノロール上の単音入力とフォーカスを検証する。
4. 操作音価と実音価の分離、音価正規化を実装する。
5. タイで接続した音符列の伸縮・移動と小節またぎを検証する。
6. 和音、複数声部、上下段の操作を追加する。
7. 休符・音名表記・MusicXMLとの整合を検討し、譜面出力を検証する。
8. 指番号の入力と3Dプレビューへの連携を進める。
9. MusicXML読み込み、非対応要素の検出・説明を設計する。

各段階は直線的な必須順序ではないが、譜面ドメインの判断を3D表示やファイル連携より先に固める。
