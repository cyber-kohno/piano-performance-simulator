## 1. プロジェクト概要

ソロピアノに特化した楽譜エディタと、楽譜・運指に基づいて88鍵ピアノを演奏する両手の3D映像を生成・再生するデスクトップアプリを開発する。

**最終目標**は、実在するピアニストの手元を撮影したような、見た目と動作が自然な演奏映像。

**最初のMVP**は自然さを追求しない。指定された時刻に、指定された手の指定指で、指定鍵盤を押すことを優先する。指の形は固定したまま、手全体を平行移動して押鍵・離鍵してよい。見た目が不自然になった段階で必要な機能を段階的に追加する。

> 開発原則: 最初からIK、物理エンジン、モーションキャプチャ、AI動作生成を導入しない。小さく動くものを作り、映像を確認してから拡張する。

## 2. 想定プラットフォーム・技術

- デスクトップアプリ: **Tauri**
- UI・楽譜エディタ: **Svelte + TypeScript** を第一候補
- 3D描画: **Three.js** を第一候補
- 3Dモデル作成・編集: 将来的に **Blender**
- 3Dモデル交換形式: **glTF / GLB**
- 将来のボーン制御: Three.jsの `Skeleton` / `SkinnedMesh` 等
- 将来のIK: Three.jsの `CCDIKSolver` の検証、または独自実装
- 将来の高度な計算: 必要に応じてWeb Worker / WASM
- 音声: 将来的にWeb Audio APIとピアノ音源などを検討（方式未決定）

Unityを必須とはしない。楽譜エディタと3Dプレビューを同一のWeb技術基盤で構築する方針。Babylon.jsも代替候補だが、現段階ではThree.jsを優先する。

## 3. 機能要件

### 3.1 最終的に実現したい機能

1. ソロピアノ向け楽譜をアプリ内で入力・編集する。
2. 楽譜から運指（左右の手・指番号1〜5）を算出する。自動計算やAIの利用は将来検討。手動指定・修正も想定する。
3. 楽譜と運指から演奏動作を計画・生成する。
4. 生成した演奏動作をキャッシュし、プレビュー再生する。
5. 88鍵ピアノ、左右の手、押鍵・離鍵を3Dで描画する。
6. 最終的には、自然な指・手首・前腕の動きとリアルな見た目を目指す。

### 3.2 初期MVPの範囲

- 3D技術検証を優先し、**楽譜エディタや自動運指計算はまだ実装しなくてよい**。
- 入力は、音符の開始時刻、長さ、MIDIノート番号、手、指番号を持つ静的JSON等でよい。
- 右手・単音・短い演奏列から始める。88鍵・両手対応は後続段階でよい。
- 白鍵と黒鍵のある鍵盤を3Dで表示する。
- 手は箱・円柱などの簡易形状でよい。Blender製モデルは不要。
- 手の指の形は固定し、指定指の指先が指定鍵盤の押鍵位置に合うよう、手全体を平行移動する。
- 押鍵時は手全体を下げ、対応する鍵盤も押下状態に動かす。離鍵時に戻す。
- 指関節のIK・指の開閉・物理シミュレーションは実装しない。
- 指定した指・鍵盤・時刻の対応が確認できることを重視する。

### 3.3 MVPの明確な非目標

- リアルな肌・爪・関節の表現
- 人間らしい手首・前腕の動作
- 和音・同時押鍵の一般対応
- 指くぐり、指またぎ、両手交差の自然な再現
- 衝突回避の完全保証
- 実演奏動画からの動作抽出
- AIによる動作生成
- 演奏表現・打鍵強度の厳密な再現

## 4. MVPの基本アルゴリズム

### 4.1 座標系

鍵盤ごとに、指先が触れる目標位置を定義する。白鍵と黒鍵では接触面の高さ・奥行きが異なるため、鍵盤番号だけでなく**接触位置**を持つ。

手のモデルには、手のローカル座標系で各指先の位置を定義する。モデルを差し替えた際には、指先位置のキャリブレーションが必要。

手の向きが固定なら、目標となる手の位置は概念的に次の式で計算できる。

```text
handWorldPosition = keyTargetWorldPosition - rotatedFingerLocalPosition
```

ここで `rotatedFingerLocalPosition` は、固定された手の回転を指先のローカル座標へ適用した値。親Groupの変換階層がある場合は、その変換も正しく扱うこと。

### 4.2 最小動作

1. 次に弾く音符の鍵盤と指を特定する。
2. 指先が対象鍵盤の上に来る位置へ、手全体を移動する。
3. 押鍵時刻に合わせて手全体を下げる。
4. 対象鍵盤を下げる（簡易表現では平行移動でもよい。最終的には実際の鍵盤の支点回転を検討）。
5. 音符の終了に合わせて手と鍵盤を戻す。
6. 次の音符へ移動する。

最初は移動を線形補間してよい。時間設計は仮の定数から開始し、演奏データとの整合性を確認して調整する。

### 4.3 MVPで許容する不自然さ・制約

- 他の指が別の鍵盤に近づいたり、場合によってはめり込んだりしても、最初は既知の制約として許容する。
- 指定指以外の指で別の鍵盤を押したことにはしない（鍵盤の動作は音符データから制御）。
- 同一の手で音符が重なる場合、固定姿勢の手を1箇所にしか置けない。**未対応ケースとして検出し、無理に正しい動作を生成したことにしない**。
- 左右の手の同時演奏は、各手を独立制御する段階で追加する。
- 音符の長さと鍵盤を押し続ける時間の扱いは、初期仕様として明示する。

## 5. 段階的な開発ロードマップ

### Level 0 — 固定姿勢・単音演奏（最優先）

- Three.jsのみで鍵盤と簡易的な片手を構築
- 各指先のローカル座標を定義
- 指定指を目標鍵盤に合わせて手全体を移動
- 押鍵・離鍵の手の上下動と鍵盤アニメーション
- JSONの短い単音列を時系列で再生
- 動作の不自然さを実際に確認

**完了条件:** 指定した指で指定鍵盤を、指定時刻に押す一連の3Dプレビューができる。既知の未対応ケースは明示される。

### Level 1 — 押鍵する指の簡易ボーンアニメーション

- リグ付きの手モデルを導入（または簡易ボーンモデル）
- 指定した指だけを固定パターンで曲げる
- 指の曲げ・戻しと鍵盤動作を同期
- IKはまだ導入しなくてよい

**完了条件:** 固定姿勢のMVPと比較し、押鍵の視覚的な自然さが改善される。

### Level 2 — 指の開閉・和音対応

- 手のひらの位置・向きと各指の姿勢を分離
- 複数指の同時押鍵を扱う
- 届かない和音・不可能な運指を検出
- 必要な範囲で手首や指の角度を調整

**完了条件:** 代表的な和音を、指定した複数指で押鍵できる。

### Level 3 — IK・姿勢計算

- 指先の目標座標から関節角度を求める
- 関節可動域、接触、他の指との干渉を考慮
- 手首・手のひらの姿勢計算
- 指くぐり、跳躍、黒鍵などを段階的に扱う

**完了条件:** より多様な譜面に対し、破綻の少ない演奏動作を生成できる。

### Level 4 — 自然な演奏表現

- 前後の音を考慮した動作計画
- 手首・前腕の自然な移動
- モーションキャプチャ由来の参考動作の利用を検討
- 姿勢最適化・衝突回避・指先の接触品質改善
- リアルなモデル・材質・照明

**完了条件:** 人間のピアニストの手元映像に近づけるための品質評価を継続できる。

> 各Levelの着手は、前Levelの映像を見て必要性を判断する。ロードマップは一括実装の指示ではない。

## 6. 推奨アーキテクチャ

```text
Tauri + Svelte + TypeScript
├── Score Editor（後続フェーズ）
├── Fingering Engine（後続フェーズ）
├── Performance / Motion Engine
│   ├── FixedHandMotionEngine（MVP）
│   ├── FingerMotionEngine（将来）
│   └── IKMotionEngine（将来）
├── Motion Cache / Timeline
├── Three.js Renderer
│   ├── Keyboard
│   ├── LeftHand / RightHand
│   └── Camera / Lighting
└── Audio / Playback Sync（後続フェーズ）
```

**重要:** 動作生成と3D描画を分離する。レンダラーは動作生成アルゴリズムに依存せず、指定時刻の姿勢を描画する。

MVPの実装で過剰な抽象化は避ける。ただし、入出力の境界は明確にする。

### 入力データの概念例

```ts
type NoteAction = {
  time: number;         // 秒。開始時刻
  duration: number;     // 秒。初期仕様では押鍵保持時間として扱う
  midiNote: number;     // 21〜108が88鍵ピアノの範囲
  hand: 'left' | 'right';
  finger: 1 | 2 | 3 | 4 | 5;
};
```

MVPでは手動定義の配列でよい。将来的に楽譜データからこの中間表現を生成する。

### 姿勢出力の概念例

```ts
type HandPose = {
  position: [number, number, number];
  rotation: [number, number, number, number]; // quaternion
  joints?: Record<string, number>; // MVPでは不要、将来用
};

type PerformanceFrame = {
  time: number;
  leftHand?: HandPose;
  rightHand?: HandPose;
  keys: { midiNote: number; depth: number }[];
};

interface MotionEngine {
  generate(notes: NoteAction[]): PerformanceAnimation;
}
```

`PerformanceAnimation` の具体的な表現は未定義。全フレーム保存ではなく、キーフレーム・イベント・補間規則などの軽量な表現を優先して検討する。上記は設計イメージであり、確定APIではない。

### 再生方式

- フレーム更新回数に依存して位置を累積するのではなく、**再生時刻から姿勢を評価**する設計を推奨。
- 停止、シーク、速度変更、コマ送りに拡張しやすくする。
- アニメーションの生成・キャッシュと、再生・描画は分離する。
- 音声同期の具体的な基準時計は後続フェーズで決定する。

## 7. 3Dモデルに関する方針

### MVP

- Blender不要。Three.jsの基本形状で手のひら・指・鍵盤を作る。
- 指は固定姿勢でよい。各指先の接触点を明示する。
- 鍵盤と手の寸法・座標系を揃える。

### 将来

- Blender等でリグ付きモデルを作成・調達し、GLBでThree.jsへ読み込む。
- メッシュ、ボーン、スキニング、ウェイト、指先の基準点が必要。
- 前腕まで含むモデルを検討する。
- 関節の回転軸・可動域・命名規則を仕様化する。
- BlenderのMCPを使ったAI支援制作は試してよいが、品質と骨格仕様の検証が必要。
- Blender固有のIK制約がGLB経由でそのまま動くとは想定せず、ランタイムのIKはアプリ側で実装する。

## 8. 将来の高度化で検討する技術

- **FK（順運動学）:** ボーン角度から指先位置を求める。
- **IK（逆運動学）:** 指先の目標位置から関節角度を求める。
- **姿勢最適化:** 接触、関節制約、滑らかさ、衝突、自然さを評価する。
- **モーションキャプチャ:** 実演奏の動作を収集し、プリセットや参照データとして利用する。
- **MediaPipe Hand Landmarker:** 動画から手のランドマークを推定する候補。ただし遮蔽や3D推定誤差に注意。
- **機械学習による動作生成:** 長期的な研究対象。初期段階では不要。
- **接触モデル:** 鍵盤の沈み込みと指先の位置を整合させる。

## 9. 技術的リスクと留意点

1. **固定姿勢の限界:** 同じ手の複数指を独立して鍵盤へ合わせられないため、一般的な和音に非対応。
2. **干渉:** 対象外の指が鍵盤にめり込む可能性がある。MVPでは許容しつつ可視化・検出を検討。
3. **黒鍵:** 白鍵と高さ・奥行きが異なる。鍵盤別の接触位置を定義する。
4. **モデル差し替え:** 指先のローカル座標・姿勢基準の再調整が必要。
5. **タイミング:** 音符の開始・終了と手の移動開始・押鍵・離鍵の関係を明示する。
6. **リアリティ:** モデルの見た目と、自然な人体動作の生成は別問題。段階的に評価する。
7. **計算量:** 将来の全関節・全時刻の最適化は高コストになり得る。必要になってから導入する。

## 10. Codexへの引継ぎ指示

この文書は開発方針を示すものであり、**全機能を一度に実装する指示ではない**。

初回の作業では、まず以下を行うこと。

1. この文書を読み、MVPのスコープと未決事項を短く整理する。
2. Three.jsで固定姿勢の簡易手モデルと鍵盤を動かす最小プロトタイプの構成を提案する。
3. 座標系、鍵盤寸法、指先の接触点、押鍵タイミングの設計を示す。
4. 実装を小さなステップに分割し、ユーザーの確認を得てから着手する。
5. まずは右手・単音・数鍵で動作を検証する。初回から88鍵、楽譜エディタ、運指AI、IKを作り込まない。
6. 実装した機能・未対応ケース・次の改善候補を記録する。

### 最初の検証シナリオ

- 右手の固定姿勢モデルを表示する。
- 指番号2（人差し指）でC4を押す。
- 指番号3（中指）でD4を押す。
- 指番号1（親指）でE4を押す。
- いずれも手全体を移動して押鍵・離鍵する。
- 鍵盤の押下アニメーションと手の移動が視覚的に確認できる。

### 未決事項（実装前または進行中に確認）

- 楽譜エディタと3Dプロトタイプの統合時期
- 画面視点（真上、斜め上、演奏者視点など）
- 実際の鍵盤寸法と3D単位の取り決め
- 最初の手モデルの基準姿勢・指先座標
- 押鍵前の移動時間と補間方法
- 単音以外の入力が来た場合のエラー・警告方針
- 再生UIの最小要件
- 将来のキャッシュ形式・永続化形式

## 11. 開発方針のまとめ

- **最終目標はリアルな演奏映像。MVPは指定指・指定鍵盤の正確な対応。**
- 固定姿勢の手を丸ごと動かすところから始める。
- 最初はIK、物理演算、Blender、AIを使わない。
- 目で確認した不自然さに応じて、指の曲げ、和音、IK、自然な動作へ拡張する。
- 演奏動作生成とThree.js描画は分離する。
- 各段階で理解・検証しながら進め、過剰な一括自動実装は避ける。
